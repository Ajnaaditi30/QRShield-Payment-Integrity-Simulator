# PROJECT: QRShield — QR Payment Integrity Simulator

Act as a senior full-stack developer, cybersecurity engineer, and UI/UX designer. Build a complete, functional, visually impressive cybersecurity microproject called **QRShield — QR Payment Integrity Simulator**.

Do not create just a landing page or static UI mockup. Build a working full-stack application with a React frontend and Python FastAPI backend. All major buttons, forms, navigation links, QR generation, tampering actions, verification results, and history records must work.

The project is an academic cybersecurity demonstration. It simulates QR payment payload tampering using fictional data. It must never initiate real payments or connect to UPI or banking services.

---

## 1. PROJECT OBJECTIVE

QRShield demonstrates how an attacker could modify payment information embedded in a QR code and how a digital integrity mechanism can detect unauthorized changes.

The application should allow a user to:

1. Generate a QR code containing fictional payment information.
2. Display and inspect the original payment payload.
3. Simulate an attacker modifying the recipient, amount, or multiple fields.
4. Compare the original and modified payloads.
5. Verify the payload's integrity using HMAC-SHA256.
6. Display a clear security result indicating whether the signed data has been altered.
7. View a session-based history of generated QR codes, tampering simulations, and verification attempts.

The application should help students understand QR payment security, data integrity, message authentication, and tampering detection.

## 12. SECURITY IMPLEMENTATION REQUIREMENTS

Implement these carefully.

### HMAC signing

- Use Python's `hmac` and `hashlib`.
- Use HMAC-SHA256.
- Load the signing secret from an environment variable such as `QRSHIELD_HMAC_SECRET`.
- For local development only, document a safe way to configure a demo secret.
- Never hardcode a production secret.
- Never send the secret to the frontend.
- Never include the secret in logs or API responses.

### Canonical serialization

Create a single backend function that serializes the signed fields consistently, such as with deterministic JSON serialization using sorted keys and fixed separators.

Use the same canonicalization logic for signing and verification.

Only include explicitly defined signed fields. Ensure that changes to any security-relevant field cause verification to fail.

### Signature verification

Use `hmac.compare_digest` to compare signatures.

Reject missing, malformed, or invalid signatures safely.

Do not trust a client-provided field such as `is_valid`, `verified`, or `tampered` to determine the result.

The backend must calculate the result independently.

### Input validation

- Validate all request bodies with Pydantic.
- Reject negative or zero amounts.
- Limit text-field lengths.
- Validate signature format.
- Handle malformed JSON.
- Return clear HTTP error responses.
- Avoid exposing stack traces or internal secrets.

### CORS and configuration

Configure CORS for the frontend origin required by the actual development environment. Do not blindly allow every origin in production.

Document any necessary Replit-specific networking configuration.

### Session history

Since this project must not use a database, use a simple in-memory history list with a reasonable maximum event count. State clearly that history is temporary.

If multiple browser users share the same backend process, history may be shared between them. Do not describe this implementation as private per-user history unless proper session isolation is implemented.
